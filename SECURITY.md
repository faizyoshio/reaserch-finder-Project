# Security & Authentication Implementation Guide

## Overview

This document outlines the comprehensive security measures implemented in ResearchFinder to protect user data and prevent common web vulnerabilities.

---

## 1. Authentication & Authorization

### Email Verification
- **Process**: Users must verify their email via OTP (One-Time Password) before account activation
- **Protection**: Prevents account takeover via fake emails and reduces spam accounts
- **Implementation**: 6-digit OTP sent to registered email, valid for 24 hours
- **Security**: OTP is cryptographically generated by Supabase and never stored in plaintext

### Session Management
- **Type**: HTTP-only cookies managed by Supabase
- **Protection**: Prevents XSS attacks from stealing session tokens
- **Refresh**: Automatic token refresh on page reload
- **Expiry**: Sessions expire after 24 hours (configurable)

### Rate Limiting
- **Login Attempts**: 5 attempts per 15 minutes per IP
- **Signup Attempts**: 5 attempts per 15 minutes per IP
- **OTP Verification**: 10 attempts per 15 minutes per IP
- **Protection**: Prevents brute force and credential stuffing attacks

---

## 2. Password Security

### Requirements
- **Minimum Length**: 8 characters (NIST SP 800-63B standard)
- **Maximum Length**: 128 characters (prevents DoS attacks)
- **Complexity**: Must contain:
  - At least one uppercase letter
  - At least one lowercase letter
  - At least one number
  - At least one special character (!@#$%^&* etc)

### Storage
- **Hashing**: bcrypt with salt rounds (handled by Supabase Auth)
- **Never Stored**: Plaintext passwords never stored in database
- **Transmission**: Always sent over HTTPS

### Weak Pattern Detection
- Prevents common passwords: `password`, `123456`, `qwerty`, etc.
- Detects sequential patterns and keyboard walks
- Strength meter provides real-time feedback to users

---

## 3. Input Validation & Sanitization

### Email Validation
- **Standard**: RFC 5322 compliant email regex
- **Length**: Maximum 254 characters (RFC 5321)
- **Disposable Emails**: Blocked (tempmail, guerrillamail, etc.)
- **Format**: Strict validation prevents injection attacks

### Search Query Validation
- **Minimum Length**: 5 words (prevents trivial searches)
- **Maximum Length**: 500 characters
- **Sanitization**: Escapes HTML special characters
- **Injection Prevention**: Detects and blocks SQL/XSS patterns

### XSS Prevention
- **Input Escaping**: All user inputs are HTML-escaped
- **Output Encoding**: React automatically escapes by default
- **Content-Security-Policy**: Restricts inline scripts and external resources
- **Detection**: Blocks inputs containing:
  - `<script>` tags
  - JavaScript event handlers (onclick, onload, etc.)
  - `javascript:` protocols
  - `eval()` expressions

### SQL Injection Prevention
- **Parameterized Queries**: All database queries use Supabase client with automatic parameterization
- **Pattern Detection**: Detects common SQL injection patterns:
  - UNION/SELECT combinations
  - OR statements
  - DROP/DELETE/INSERT/UPDATE/EXEC commands
  - SQL comment markers (--,  #, /* */)
- **No String Concatenation**: Raw SQL never constructed from user input

## 4. Database Security

### Row-Level Security (RLS)
- **Enforcement**: Every table has RLS policies enabled
- **Saved Articles**: Users can only view/edit/delete their own articles
- **Policies**:
  ```sql
  -- Users can only view their own saved articles
  CREATE POLICY "Users can view their own saved articles"
    ON saved_articles
    FOR SELECT
    USING (auth.uid() = user_id);
  
  -- Similar policies for INSERT, UPDATE, DELETE
  ```

### Data Integrity
- **Constraints**: Unique constraint on (user_id, article_id)
- **Timestamps**: Automatic created_at and updated_at tracking
- **Cascading Deletes**: Saved articles deleted when user account deleted

### Audit Logging
- **Action Tracking**: All auth actions logged to audit_logs table
- **Metadata**: IP address, action type, resource ID stored
- **User Access**: Users can view their own audit logs for transparency

## 5. API Security

### Authentication
- **Required**: All protected endpoints check for valid Supabase session
- **Rejection**: Returns 401 Unauthorized if no session
- **Headers**: Authorization header validated for every request

### Request Validation
- **Content-Type**: Validates JSON content type
- **CSRF Protection**: Next.js built-in protection via cookies
- **Method Validation**: Explicit HTTP method handling (GET, POST, DELETE)

### Response Security
- **No Sensitive Data**: Error messages don't expose system details
- **Generic Messages**: "Invalid email or password" instead of "Email not found"
- **Email Enumeration**: Prevented by generic error messages

### Rate Limiting
- **Implementation**: In-memory rate limiter (client IP based)
- **Production**: Should use Redis for distributed systems
- **Response**: HTTP 429 (Too Many Requests) when limit exceeded

## 6. HTTP Security Headers

### Headers Implemented
```
X-Frame-Options: DENY                    # Clickjacking prevention
X-Content-Type-Options: nosniff          # MIME sniffing prevention
X-XSS-Protection: 1; mode=block          # XSS protection (older browsers)
Referrer-Policy: strict-origin-when-cross-origin  # Referrer privacy
Content-Security-Policy: [strict policy] # XSS and injection prevention
Strict-Transport-Security: max-age=31536000 # HTTPS enforcement
Permissions-Policy: camera=(), microphone=(), geolocation=() # Feature restriction
Cache-Control: no-store (on auth pages)  # Prevent caching sensitive data
```

### Protection Coverage
- **XSS**: CSP blocks unsafe scripts and eval
- **Clickjacking**: X-Frame-Options prevents framing in iframes
- **MIME Type Confusion**: X-Content-Type-Options forces type enforcement
- **Man-in-the-Middle**: HSTS enforces HTTPS for 1 year

## 7. Frontend Security

### Component Security
- **Auth Context**: Provides centralized auth state management
- **Protected Routes**: Automatically redirects unauthenticated users
- **Session Persistence**: User session maintained across page reloads

### Sensitive Information
- **No localStorage**: Auth tokens handled by Supabase (HTTP-only cookies)
- **No Password Storage**: Passwords never stored client-side
- **No API Keys**: API keys only used server-side

### Protected Routes
- `/saved` - Requires authentication (redirects to /auth/login if not logged in)
- `/auth/verify` - OTP verification page
- `/auth/login` - Login page
- `/auth/signup` - Registration page

## 8. Email Verification Security

### Flow
1. User signs up with email/password
2. Supabase generates 6-digit OTP and sends via email
3. User enters OTP on verification page
4. OTP validated server-side with rate limiting
5. Account activated upon successful verification

### Protection
- **OTP Format**: 6 digits only (prevents brute force)
- **Expiry**: 24 hours (prevents old OTP reuse)
- **Rate Limited**: 10 attempts per 15 minutes
- **IP Tracked**: Logged for security monitoring
- **No Resends During Verification**: Prevents flooding

## 12. Incident Response

### If Account Compromised
1. User changes password immediately
2. All active sessions invalidated
3. Audit log reviewed for suspicious activity
4. User notified of login attempt from unusual location

### If Data Breach Detected
1. Incident declared immediately
2. Affected users notified within 24 hours
3. Database backed up for forensics
4. Rate limiting increased
5. Security audit scheduled
